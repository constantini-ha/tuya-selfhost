# Controlling a device your blaster has no protocol for

> 🇧🇷 [Português](LEARNED_REMOTES.pt-BR.md) · 🇪🇸 [Español](LEARNED_REMOTES.es.md)

Protocol integrations such as `gree_infrared` only work when your appliance
really speaks that protocol. Plenty of air conditioners, TVs and fans sold under
local brands do not, and no amount of configuration will change that.

The way out is to stop guessing the protocol and copy the signal instead: teach
the blaster your physical remote, then replay it.

## The easy way: the Tuya Selfhost panel

The integration ships a builder. Open **Tuya Selfhost** in the sidebar, create a
control, add buttons with a name and an icon, and teach them one at a time. Each
capture offers **Test / Keep / Discard**, so a bad reading never silently
replaces a good one, and the arrows under each button set its position.

When the control is ready, **Add to dashboard** drops the finished card into your
first view. Everything below is the same thing done by hand, for anyone who
prefers YAML or needs it inside an automation.

## The one thing to understand first

**Air conditioner remotes do not send "one degree warmer".** Every press
transmits the *entire* state — power, mode, temperature, fan speed, swing — in a
single frame. So there is no "+" button to learn; "cool at 22" and "cool at 23"
are two completely different codes.

This is why a protocol integration either works entirely or not at all, and why
learning only the states you actually use is the sensible approach. Three or four
codes cover normal life.

## Learning a code

Point the physical remote at the blaster, about 20 cm away, then call:

```yaml
action: remote.learn_command
target:
  entity_id: remote.your_blaster
data:
  device: ac
  command: "on_cool_22"
```

A notification appears and you have 30 seconds to press the button. Set the
remote to the exact state you want *before* pressing, because that whole state is
what gets captured.

Useful codes to start with: turning on at your usual temperature, turning off,
and one colder and one warmer setting.

## Replaying it

```yaml
action: remote.send_command
target:
  entity_id: remote.your_blaster
data:
  device: ac
  command: "on_cool_22"
```

Raw codes work too, without learning anything, if you already have them from
another source:

```yaml
data:
  command: "b64:JgBQAAABKJM..."
```

## A dashboard card

This is the pattern, with a learning button so you can add codes without editing
anything:

```yaml
type: grid
cards:
  - type: heading
    heading: Air conditioner
  - type: horizontal-stack
    cards:
      - type: button
        name: On
        icon: mdi:air-conditioner
        show_state: false
        tap_action:
          action: perform-action
          perform_action: remote.send_command
          target:
            entity_id: remote.your_blaster
          data:
            device: ac
            command: on_cool_22
      - type: button
        name: Off
        icon: mdi:power
        show_state: false
        tap_action:
          action: perform-action
          perform_action: remote.send_command
          target:
            entity_id: remote.your_blaster
          data:
            device: ac
            command: "off"
  - type: button
    name: Learn "off"
    icon: mdi:school-outline
    show_state: false
    tap_action:
      action: perform-action
      perform_action: remote.learn_command
      target:
        entity_id: remote.your_blaster
      data:
        device: ac
        command: "off"
```

## What you give up

Infrared is one way. Home Assistant knows what it sent, never what the appliance
did, and a press on the physical remote is invisible to it. Buttons are honest
about this in a way a thermostat dial is not — the dial implies a state Home
Assistant cannot actually read.

## Your codes survive a device swap

Learned codes are stored per device id. If you ever re-pair the blaster in the
Tuya app it gets a new id, which used to orphan every code you had taught it. Use
**Reconfigure** on the entry instead of deleting it and the codes travel with it.

## Pressing a key by voice

Every key you teach also becomes a `button` entity, named `<remote> <key>` and
grouped under the emitter. That is what makes it reachable from an automation, a
script, or a voice assistant.

Alexa treats a button as a scene, so the phrase is *turn on*:

> "Alexa, turn on Living room AC Cool 22"

The block generated by the **Alexa configuration** action already carries a glob
covering every key, present and future, so you never have to regenerate it after
teaching one more. Teaching a key also hands it to Alexa on the spot, so there is usually nothing
left to do. Home Assistant itself only does that for Nabu Casa accounts; the
integration does it for a self-hosted skill too.

If a key does not turn up — Alexa was unreachable, or you set the skill up after
teaching it — the Alexa tab in the panel has **Send the keys to Alexa**, and the
`tuya_selfhost.alexa_announce` action does the same from an automation. Failing
both, the old way still works:

> "Alexa, discover devices"

One thing to check if nothing arrives at all: your `alexa:` filter has to let
buttons through. A filter that only says `include_domains: [switch]` drops every
key, and no discovery will change that. The generated block gets this right.

[Exposing your devices to Alexa](ALEXA.md) covers the rest, and
[Building the Alexa skill from scratch](ALEXA_SKILL.md) covers the skill itself.

### An on/off pair is better than two scenes

A single key is a one-shot, so Alexa can only see it as a scene. A pair — one
key that switches the appliance on, one that switches it off — is a **device**,
and that is worth setting up: "turn on the air conditioning" and "turn off the
air conditioning" both work, which is how anyone expects to talk to an
appliance.

In **Edit**, under **Power pair**, pick the key that turns it on and the key
that turns it off. The two stop being scenes and become one switch.

Each remote is a device of its own in Home Assistant, named as you named it and
listed under the emitter — a blaster holds a television, an air conditioner and
a fan, and each should answer to its own name. So the switch reads as
"Living room AC", and a key as "Living room AC Cool 22".

Infrared is one way, so the switch cannot know what the appliance is really
doing: it shows what was last sent. Home Assistant marks it as an assumed state
and draws two buttons instead of a toggle.

Everything else stays a scene, which suits a one-shot key like "Cool 22".

On the dashboard the remote's card follows: the switch sits at the top, with the
state and a power button, and the loose keys fill the grid underneath. The two
paired keys are not drawn twice.

### Naming a key so Alexa understands it

Alexa sees a button as a **scene**, and a scene only answers to *turn on*. There
is no *turn off*: a key that switches the appliance off is its own scene, and it
needs a name that reads naturally after "turn on".

The name Alexa gets is the entity's, which Home Assistant builds as
`<emitter> <remote> <key>` — far too long to say. Give it a short one in the
`entity_config` section of your `alexa:` block:

```yaml
      button.tuya_remote_living_room_ac_on:
        name: Air conditioning
      button.tuya_remote_living_room_ac_off:
        name: Air off
```

Then "Alexa, turn on the air conditioning" and "Alexa, turn on air off". The
second reads oddly in English; an Alexa routine in the app can map any phrase
you like onto the scene, which is the usual way around it.

Change a name and the key has to go out again: the **Send the keys to Alexa**
button does that. A key you delete here is dropped from Alexa automatically, and
`tuya_selfhost.alexa_announce` takes a `forget` list for scenes left over from
before this was handled.
